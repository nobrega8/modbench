\chapter{Command line and AI assistants}

\file{modbench-cli} reads devices and works with maps without the window: for
scripts, for servers without a screen, and for a quick check. It comes with
the app. It never writes to a device.

\section{Commands}

\begin{lstlisting}[language=bash]
modbench-cli read --tcp 192.168.1.10 holding 0x0405 1
modbench-cli read --udp 192.168.1.10 holding 0 10
modbench-cli read --tcp 192.168.1.10 --source 192.168.1.5 holding 0 2
modbench-cli map --rtu COM3 --unit 18 device.mbmap.json --filter voltage
modbench-cli scan --rtu COM3 --baud 9600 --from 1 --to 32
modbench-cli id --tcp 192.168.1.10
modbench-cli simulate device.mbmap.json --strict
modbench-cli simulate device.mbmap.json --generators moving.json
modbench-cli simulate device.mbmap.json --rtu-over-tcp
modbench-cli simulate device.mbmap.json --rtu COM5 --baud 19200 --parity E
modbench-cli validate device.mbmap.json
modbench-cli convert old-device.mbmap
\end{lstlisting}

\begin{center}
\begin{tabularx}{\linewidth}{l L}
  \toprule
  \thead{Command} & \thead{What it does} \\
  \midrule
  \val{read} & Reads coils or registers, like a manual request. \\
  \val{map} & Reads every register of a map from a device, by name;
    \val{--filter} keeps the names that match. \\
  \val{scan} & Finds the unit IDs that answer. \\
  \val{id} & Device identification (FC43). \\
  \val{simulate} & A simulated device shaped after a map (port 5020 by
    default); \val{--strict} answers only the map's addresses. \\
  \val{validate} & Checks a map against the format, with the same messages as
    the app. \\
  \val{convert} & Converts a version 1 map to a \file{.mbmap.json} next to it. \\
  \bottomrule
\end{tabularx}
\end{center}

\val{modbench-cli --help} lists every command and option, and
\val{modbench-cli --version} prints the version; \val{-h} and \val{-V} are
short for them. \val{modbench --help} and \val{modbench --version} answer the
same way for the app, without opening its window. A wrong argument prints an
error and exits with code 2.

\section{Generators file}

\val{--generators} takes a JSON list. Each entry names a map register (in
engineering units) or a raw \val{area} and \val{address}, a \val{kind}, and how
often it changes (\val{every\_ms}, 1000 by default, at least 50):

\begin{lstlisting}
[
  {"register": "Voltage L1", "kind": "sine", "offset": 230, "amplitude": 5, "period_s": 10, "every_ms": 500},
  {"area": "input", "address": 0, "kind": "increment", "step": 1, "min": 0, "max": 100},
  {"area": "holding", "address": 1, "kind": "random", "min": 10, "max": 20},
  {"area": "discrete", "address": 0, "kind": "copy", "from": {"area": "coil", "address": 0}}
]
\end{lstlisting}

\section{AI assistants (MCP)}

\val{modbench-cli mcp} serves the same reads over the Model Context Protocol
(stdio), so an AI assistant such as Claude Code can read devices and check
maps: \val{read\_map} reads a device with a map, \val{validate\_map} checks a
map file. Like the command line, it never writes to a device.

\subsection{Letting an assistant drive the window}

The tools above run in their own process. To let an assistant work in the
Modbench window you are looking at, turn on \emph{Let an assistant control
Modbench} in Settings, Connection. It is off by default. Modbench then listens
on a loopback port only, and writes the port and a random token to a file in
its data folder; \val{modbench-cli mcp} reads that file and forwards the
\val{gui\_*} tools to the window. Without a running window, or with the setting
off, those tools say so and the others keep working.

\begin{description}[style=nextline, leftmargin=0pt, font=\intermedium]
  \item[gui\_get\_state] The visible state as JSON: connection, open maps,
    registers and their latest values, the screen shown. Read it first.
  \item[gui\_set\_connection] Transport, host or serial port, port, baud rate,
    parity, stop bits, unit ID, timeout.
  \item[gui\_list\_library, gui\_open\_map] Browse the library and open a map.
  \item[gui\_set\_map\_view] Address notation, byte order, which registers are
    read.
  \item[gui\_set\_manual\_read] Function code 1 to 4, address and quantity.
  \item[gui\_run] Start or stop reading, with Loop and its interval.
  \item[gui\_chart] The registers on the Chart tab.
  \item[gui\_navigate] The page, tab or tool shown.
\end{description}

What you can rely on:
\begin{itemize}
  \item Every change happens in the window, so you see it as it is made, and
    a bar shows that an assistant is connected, with a list of what it did.
  \item \emph{Pause} turns every request down until you resume it.
    \emph{Disconnect} drops the assistants and changes the port and token.
  \item While a test runs, the connection, the map and the manual read cannot
    be changed; stop the test first.
  \item It never writes to a device: manual requests are limited to the read
    function codes, and a manual request that is a write is not started.
    Read-only mode and the write confirmation are therefore not needed for it,
    and stay as they are for you.
  \item Only programs running as your user can read the token file.
\end{itemize}
